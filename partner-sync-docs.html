Partner Sync API

Create, update, read, and deactivate partners from an external system (HighLevel form → Zapier → this endpoint). Everything is keyed by the HighLevel contact id.
One endpoint, four verbs. Base URL: https://portal.mypayprotec.com/api/partner-sync

Authentication

Send the shared secret on every request as the x-api-key header (or Authorization: Bearer <key>). The secret is stored server-side as the Vercel env var PARTNER_SYNC_KEY.

x-api-key: psk_live_your_secret_here
Keep this secret private — anyone with it can create/modify partners. Rotate it by changing PARTNER_SYNC_KEY in Vercel.

The unique key

Every request identifies the partner by hl_contact_id (the HighLevel contact id). It maps to persons.hl_contact_id in the app — the single dedup key. If a partner with that id exists, writes update it; otherwise they create it.

No separate "search" step needed in Zapier. A single POST already does search-then-create-or-update: if the hl_contact_id is found, it updates that partner (adds/updates agent IDs, prime49, approval date, company); if not found, it creates the partner, company, agent IDs, and prime49/approval in one call. Just send the same POST every time the HighLevel form fires — no branching/lookup logic required in your Zap.

Agent IDs — accepted formats

// simplest — comma-separated, one prime49 + rev_share for all
"agent_ids": "AGENT001, AGENT002", "prime49": true, "rev_share": 50

// or an array of strings
"agent_ids": ["AGENT001", "AGENT002"]

// or per-ID objects (advanced — different prime49/rev_share per ID)
"agent_ids": [{"id_string":"AGENT001","prime49":true,"rev_share":50}]

Endpoints

GET/api/partner-sync?hl_contact_id=<id>

Read a partner: name, email, phone, business name, agent IDs (with prime49 + rev_share + status), portal status.

curl "https://portal.mypayprotec.com/api/partner-sync?hl_contact_id=ABC123" \
  -H "x-api-key: psk_live_your_secret"
POSTPUT/api/partner-sync

Create-or-update (idempotent). POST and PUT behave the same — you never have to know if the partner already exists. Returns 201 on create, 200 on update.

curl -X POST "https://portal.mypayprotec.com/api/partner-sync" \
  -H "x-api-key: psk_live_your_secret" \
  -H "Content-Type: application/json" \
  -d '{
    "hl_contact_id": "ABC123",
    "full_name": "Jerry Pierce",
    "email": "jerry@alt-pay.net",
    "business_name": "Alt-Pay LLC",
    "agent_ids": "AGENT001, AGENT002",
    "prime49": true,
    "rev_share": 50,
    "approved_date": "2026-07-08"
  }'
DELETE/api/partner-sync?hl_contact_id=<id>

Soft delete — the partner's agent IDs are set to inactive, portal access is disabled, and any live sessions are ended. The record and its history are kept (merchants stay linked). Reversible by sending a POST/PUT again.

curl -X DELETE "https://portal.mypayprotec.com/api/partner-sync?hl_contact_id=ABC123" \
  -H "x-api-key: psk_live_your_secret"

The end-to-end flow

This is a trigger → transform → write pipeline, all happening in Zapier before it ever touches the portal:

  1. Trigger: the HighLevel form submission fires a webhook into Zapier (HighLevel's native trigger, or a Webhook step on the form/workflow).
  2. Transform: inside the Zap, map the HighLevel custom fields (Agent IDs, Business Name, Prime49, Approval Date, etc.) onto this API's field names.
  3. Write: a Webhooks by Zapier → Custom Request action sends that mapped JSON to POST /api/partner-sync on the portal, which does the actual search-or-create/update in the database.

Nothing about HighLevel's field structure needs to match the portal's schema — Zapier is where you translate one into the other. The portal side only ever sees the field names below.
